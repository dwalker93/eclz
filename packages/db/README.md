# @workspace/db

Database package for the student management system: Drizzle ORM schema and migrations for PostgreSQL.
Built from design v1.0 (frozen). A plain-language guide to every table is in `docs/tables.md`. The design lives in `docs/`: the ER diagram and the invariants file,
where every rule says whether it is enforced by the database, a transaction, application code, or a job.

**All five phases are done** (69 tables). Two optional extras need no tables (see phase 5 below).

## What is in phase 1

organization, branch, user, file, role, permission, role_permission, staff_role_assignment, audit_log,
lecturer, lecturer_branch, student, student_branch, grade_level, guardian, student_guardian,
academic_term, subject, course_group, course, course_grade_level, course_lecturer, intake, enrollment,
schedule_slot, class_session, attendance, promotion_run, promotion_item, student_level,
fee_structure, fee_rate, invoice, invoice_item, payment_method, bank_account, payment,
payment_allocation, receipt, receipt_counter, content_item, content_branch, course_section,
course_content, notice, notice_target.

## What phase 2 adds (10 tables)

installment_option, invoice_installment, fee_exception, notification_channel, notification_template,
notification, push_subscription, message_thread, thread_participant, message. It also adds
`invoice.installment_option_id` and `invoice_item.fee_exception_id`.

The parent portal needs no tables of its own: guardians, `student_guardian` and the `parent_portal` module flag
from phase 1 are enough. Overdue restriction is also rules over existing columns (C9: grace days and action on the
organization and fee structure, `enrollment.access_status`), run by a daily job.

## What phase 3 adds (8 tables)

question, question_option, exam, exam_course, exam_question, exam_attempt, attempt_answer, exam_result.
An exam is attached to courses through `exam_course`, so branch-specific or shared is just which courses it is attached to.

## What phase 4 adds (4 tables)

content_purchase, commission_rule, commission_entry, teacher_payout. It also adds `invoice_item.content_purchase_id`
and a unique `(id, branch_id)` on `invoice`.

## What phase 5 adds (1 table)

gateway_transaction: the online payment attempt for a payment made with a gateway method (E14, unique on provider and provider reference).
It uses the same `payment` row, verification and allocation as every other method.

Not tables: Zoom and Teams automation uses the meeting columns on `class_session` from phase 1 (provider, url, ref), and
certificate-signed PDF receipts use `receipt`'s `content_hash`, `signature` and `verification_code` from phase 1. Both are application work.

## Setting up a customer deployment

1. Create the customer's PostgreSQL database and set `DATABASE_URL` in that deployment's environment (never commit it).
2. `bun run db:migrate` runs all migrations. The second one needs the `btree_gist` extension, which the database owner can create.
3. `ORG_NAME="..." ORG_TYPE=institution bun run db:seed` creates the one organization, its default branch,
   receipt counter, payment methods (bank transfer is the default), starter permissions, the built-in roles and grades 1 to 13.
4. Use the app: `import { createDb } from "@workspace/db"`.

Migrations: `0000`, `0002`, `0004`, `0006` and `0008` are generated by drizzle-kit (tables). `0001`, `0003`, `0005`, `0007` and `0009` are hand-written
for what Drizzle cannot express (constraints and triggers per phase). `0002`, `0004` and `0006` each have one line moved to the top by hand
(a unique constraint on `enrollment` or `invoice` that the new foreign keys need), so re-check the order if you regenerate them. Change the schema in `src/schema`, run `bun run db:generate`, and keep
hand-written SQL in `--custom` migrations. Write changes backward-compatible (add first, remove later) and
add a dated entry to the changelog in `docs/student-management-invariants.md`.

## Services (payments, enrolment, invoicing)

`src/services` holds the business logic that the database cannot enforce, as typed functions over Drizzle. They work with the production
`createDb` object and with PGlite in tests. Services so far: payments and receipts, enrolment, invoice generation, fee exceptions, commission accrual, yearly promotion.

```ts
import { createDb, createPaymentService, hmacSigner, verifyReceipt } from "@workspace/db";

const { db } = createDb(process.env.DATABASE_URL!);
const payments = createPaymentService(db, {
  signer: hmacSigner(process.env.RECEIPT_SIGNING_SECRET!),   // key stays out of the database
  hooks: { afterVerify, afterVoid },                          // later services join the same transaction
});

const p = await payments.submitPayment({ studentId, branchId, paymentMethodId, bankAccountId, slipFileId, amount: "1500.00", referenceNo, submittedBy });
const done = await payments.verifyPayment({ paymentId: p.id, verifiedBy, invoiceIds: [invoiceId] });  // allocate, caches, receipt
await payments.rejectPayment({ paymentId, rejectedBy, reason });
await payments.voidPayment({ paymentId, voidedBy, reason });
await payments.recordCashPayment({ studentId, branchId, amount, recordedBy, invoiceIds });
const check = await verifyReceipt(db, verificationCode, signer);   // for the public verify page
```

What they do, by rule: E3 and E4 (verification and allocation in one transaction, no advance payments), E5 (never more than an item's net outstanding,
with invoice rows locked in id order), E7 (default split: oldest due date first, pro rata across payable items with largest-remainder rounding, or explicit
item lines), E1 and E16 (invoice and installment caches re-derived in the same transaction), E8, E9 (void reverses allocations, voids the receipt),
E11 (cash), E12 and E13 (one signed receipt per payment, number from the branch counter), J3 (audit rows). Domain errors are `ServiceError` with a `code`.
Pure arithmetic (`splitProRata`, `planAllocation`, `waterfall`, status derivation, money in cents) is exported and unit tested.

Receipts: the hash is SHA-256 of a fixed-order text of the receipt number, branch, payment, student, amount, verification time and active allocations.
The signature is `signer.sign(hash)`. `verifyReceipt` rebuilds the data from the database, so any later change to the data, or a forged hash or signature, shows as invalid,
and a voided receipt shows as void. The default signer is HMAC-SHA256 with a shared secret. Use a public-key signer (same interface) if third parties must verify offline.

The row locks (`FOR UPDATE` on the payment and the invoices) cannot be exercised by PGlite, which has one connection. Before going live, run two simultaneous verifications of the same payment, and two payments on the same invoice, against a real PostgreSQL database. Both should leave consistent totals, and the second verification of one payment should fail with `payment_not_pending`.

### Enrolment, invoicing and fee exceptions

```ts
import { createEnrollmentService, createInvoicingService, createFeeExceptionService } from "@workspace/db";

const enrolment = createEnrollmentService(db);
const invoicing = createInvoicingService(db);
const exceptions = createFeeExceptionService(db);

const { enrollment, invoiceId } = await enrolment.enrollStudent({ studentId, courseId, intakeId, feeStructureId, installmentOptionId });
await enrolment.dropEnrollment({ enrollmentId, actorUserId, reason });

const report = await invoicing.generateRecurringInvoices({ branchId });   // run daily from a scheduled job; safe to run twice
await invoicing.addInvoiceLine({ invoiceId, kind: "discount", amount: "-500", appliesToItemId, description, createdBy, reason });
await invoicing.cancelInvoice({ invoiceId, cancelledBy, reason });

await exceptions.createFeeException({ enrollmentId, kind: "discount", discountType: "percent", discountValue: "25", effectiveFrom, reason, createdBy });
await exceptions.endFeeException({ exceptionId, endedBy });
```

By rule: C1 to C6 and C10 (course open, student active, intake rules, one active place, capacity counted under a lock on the course row, grade list with an audited override),
D1 (fee option: the one given, else the default, else the only active one, else `fee_structure_required`), D6 (rate by billing grade, then grade on the period start, then the all-grades rate;
a missing rate is reported and nothing is billed, never zero), D7 (one recurring line per enrolment and period, so generation is idempotent), D8 and D23 (signed lines, totals re-derived from them),
D9 and D19 (a 100% discount gives a zero `waived` invoice), D10 and D25 (installment schedule, surcharge as an adjustment line, unpaid installments re-spread after an adjustment),
D12 (package invoice at enrolment, access end = start + months), D17 to D22 (fee exceptions, module check only when creating), D24 (one invoice per student, branch and due date),
D26 (invoices are append-only: cancel only without payments), C7 (drop), B5 and B7 (grade on a date, student_branch).

Implementation choices to review:
- Monthly fees bill calendar months, starting with the month of `access_starts_on`, with no proration for a mid-month start.
- A per-term fee bills the course's academic term once (`term.starts_on` to `ends_on`). A course without a term is reported as a failure.
- Generation bills every missing period whose start is on or before today (plus `leadDays`) and before `access_ends_on`, oldest first, at most `maxPeriodsPerEnrollment` (12) per run.
- Due date is the period start plus `dueAfterDays` (7), but never before today. Periods with different due dates become separate invoices.
- A discount exception becomes a negative `discount` line linked to the fee line and the exception. An alternate option replaces the fee structure for its dates only, and the enrolment is never rewritten.
- Dates such as `enrolled_on`, `paid_on` and invoice issue dates use the organization's time zone, not UTC.
- Dropping an enrolment sets access to end today (or the next day if it started today).
- Not done yet: proration, promotion confirm (it will call `enrollStudent` with `promotedFromEnrollmentId`), and the overdue job.

### Commission accrual

```ts
import { createCommissionService, createPaymentService, combineHooks } from "@workspace/db";

const commissions = createCommissionService();
const payments = createPaymentService(db, { signer, hooks: commissions.hooks });   // or combineHooks(commissions.hooks, otherHooks)
```

Accrual runs inside the verification transaction (`afterVerify`), and reversal inside the void transaction (`afterVoid`), so a failure in either rolls the whole payment step back.
`commissions.accrue(tx, event)` returns what it created and what it skipped (with a reason such as `no_rule`), so gaps can be reported.

By rule: H1 and H2 (base = basis-adjusted allocation x the lecturer's share, one entry per allocation and lecturer, split with largest-remainder rounding),
H4 (most specific rule in effect: course, subject plus grade, subject, lecturer default; `pickRule` is exported), H5 (percent of the base; fixed per student month split by share,
accrued in proportion to what is paid, and the last payment of an item takes the remainder so the total is exact), H6 (rule, rate, share and basis snapshotted on the entry),
H7 (void: unsettled entries become `void`, settled ones get one negative reversal entry), H9 (module off: nothing accrues, but voids still unwind earlier entries),
H10 (`paid` basis uses the money allocated, `list` scales it to the list price), H11 (fee items only), H12 (commission capped at the base, `capped = true`).

Things to know:
- A lecturer with no matching rule accrues nothing (the institute keeps no commission on that fee). It shows in `skipped`.
- Course shares are not validated to sum to 100 here (H3 is checked when the course is saved), so a course whose shares sum to less than 100 simply accrues less.
- Rule dates are compared with the day of verification in the organization's time zone, not the invoice period.
- If a payment is voided after its entries joined a draft payout, a reversal is added (as for settled entries) but the draft payout's totals are not recalculated. The payout service should rebuild draft totals.
- Not done yet: teacher payouts (create, approve, pay, carry-forward of a negative net).

### Yearly promotion

```ts
import { createPromotionService } from "@workspace/db";
const promotion = createPromotionService(db);

const draft = await promotion.createDraft({ performedBy });                    // effective date defaults to the 1st of next month
await promotion.updateItem({ runId, itemId, decision: "move", toCourseId });    // review: move, stay, skip
await promotion.setEffectiveDate({ runId, effectiveDate });
const result = await promotion.confirm({ runId, confirmedBy });                 // { status: "confirmed", ... } or { status: "blocked", flagged }
await promotion.discardDraft({ runId, discardedBy });
await promotion.clearBillingGrade({ enrollmentId, clearedBy, reason });
```

By rule: B6 and B8 (draft, review, confirm once; nothing changes before confirm; students whose items are all `skip` do not advance), C12 (target = class in the same
course group that serves the next grade, otherwise same subject, branch, primary lecturer and batch label; exactly one match proposes a move, otherwise `needs_review`),
C13 (a move completes the old enrolment with `end_reason = promoted` and `access_ends_on` = the effective date, and opens a new one with `promoted_from_enrollment_id`,
the target's default fee option, and access from the effective date), C14 (the effective date is refused if it is not after the old enrolment started, or if a period past it is
already invoiced for a class being left), C15 (capacity under a lock on the target course; a full target, a duplicate or a class with no fee option is not applied),
B5 (the old grade row ends on the effective date and the new one starts on it), B7 (`student_branch`), B8 stay (billing grade pinned to the grade before promotion)
and the rule for clearing a pin (needs a reason and a fee rate for the current grade), J3 (audit on confirm and discard).

Behaviour to know:
- A draft covers every active student who has a current grade. Students with no grade (for example adults in programs) are not included. Only class enrolments are promoted, not programs.
- Confirm refuses while any item is `needs_review`. If a move cannot be placed, confirm changes nothing, flags those items `needs_review` with a note, and returns `status: "blocked"` with the list. Fix them and confirm again.
- Seats freed by students moving up in the same run count for the class behind them.
- A student with no class enrolment gets a `stay` item (grade only), and a student already at the highest grade gets `skip`.
- A draft goes stale if an enrolment in it ends before confirm (`promotion_stale`). Discard it and build a new one.
- Nothing stops two drafts existing at once. Confirm the one you want and discard the other.

Not yet in services: teacher payouts, access re-evaluation and the overdue job, exam grading. Run the service tests with `bun run db:test:services` and `bun run db:test:enrolment`.

## What the database enforces

In the Drizzle schema (checks, unique and partial unique indexes, composite foreign keys):
C1, C3, C4, D1, D2, D4, D7, D8 and D23 (item signs, discount links), D9, E6, E7 (item belongs to invoice),
E10, E12, E13, E15 (bank account branch), F1, F2, B3, A1, the primary-flag rules, and status value lists.

In the Drizzle schema, phase 2: D16 and D19 (exception columns by kind, value ranges), D17 (reason, dates),
D20 (an alternate option belongs to the enrolment's class), D21 (ended_by needs an end date), D10 (installment sequence
unique, amounts positive), J2 (one notification per user, event key and channel), and only participants can post a message.

In the Drizzle schema, phase 3: G2 (unique attempt number per exam and student, one running attempt), G3 (an attempt's enrolment
belongs to the student and the exam is attached to its course, by composite foreign keys), G5 (answers belong to the attempt's exam),
G7 (one result per exam and student, attempt results point at an attempt of the same student and exam), and mode-specific exam fields
(online needs a window and attempt limit, paper needs a date and total marks).

In the Drizzle schema, phase 4: F5 (no second pending or paid purchase of one item), F6 (handover needs a paid physical purchase and a handler),
D13 and D24 (a purchase's branch is one the item is listed in and is its invoice's branch, and its invoice is the student's), a content line must use
its purchase's own invoice (one active line per purchase), H4 scope shapes, H12 (rate ranges, an accrual's commission between 0 and its base, reversals zero or negative),
H1 (teacher amount = base minus commission), H2 (one accrual per allocation and lecturer), H7 (an entry is reversed once), H8 (a settled entry has a payout, a payout's net is gross minus commission and never negative,
and an entry's rule and payout belong to its lecturer).

In `0007_phase4_constraints.sql`: H4 no overlapping rules of one scope per lecturer (`btree_gist`), only paid content items can be purchased,
and triggers: a paid payout is immutable and payout status moves draft, approved, paid only (H8); commission entries are never deleted and only status and payout change (H6),
an accrual comes from a fee item of a course the lecturer teaches (H11), a reversal is the exact negative of an accrual of the same allocation, lecturer and rule (H12),
and nothing joins or changes inside a paid payout.

In `0005_phase3_constraints.sql` (triggers): G4 a published exam's questions cannot change and publishing needs every snapshot,
exam status moves draft to published to closed only, G7 online results come from attempts (or a manual override) while paper results are manual,
G8 a result is released only after the exam closes.

In `0003_phase2_constraints.sql`: D18, no overlapping fee exceptions of one kind on an enrolment (end-exclusive, `btree_gist`).

In `0001_phase1_constraints.sql`:
- A2 one organization per deployment
- B4 no overlapping student grade ranges, D5 no overlapping fee rates (end-exclusive ranges, `btree_gist`)
- C2 intake rule by course kind (trigger)
- E3, E4 verification and allocation are atomic: a deferred constraint trigger checks at commit that a verified
  payment's active allocations equal its amount and that other payments have none
- J4 append-only audit log (also revoke UPDATE, DELETE and TRUNCATE on `audit_log` from the app's database role)

## What is still the application's job (transactions, helpers, jobs)

These rules are in the invariants file but cannot live in the database: invoice totals equal the sum of items (insert the
invoice with its final totals, then the items), `amount_paid` and status caches (E1, E2), allocation limits (E5), the
default pro rata split across items (E7), installment waterfall (E16), capacity (C5), the access helper (C8),
overdue restriction (C9), promotion confirm (B6, B8, C12 to C15), grade lookup (B5), rate lookup (D6), receipt
numbering through `receipt_counter` (E13), commission rules and accrual, payout totals, module gates, authorization and branch scoping,
and the audit log writes (J3). Use `receipt_counter` like this inside the issuing transaction:
`UPDATE receipt_counter SET last_number = last_number + 1 WHERE branch_id = $1 RETURNING last_number`.

## Phase 5 notes for the application

- Checkout: insert the `payment` (gateway method, no bank account or slip) and its `gateway_transaction`, send the student to the provider, then handle the webhook.
- Webhook: verify the provider's signature first, find the transaction by `(provider, provider_ref)` (or by your own order id stored in `raw_payload` before the reference is known),
  and in one transaction set the transaction status, then verify and allocate the payment like any other (E3, E4). A repeated callback must change nothing (E14).
- Trigger `gateway_transaction_guard` rejects a transaction for a non-gateway payment and sets `updated_at`. Status values: initiated, succeeded, failed, cancelled (refunds are not modelled).
- Module gate: `gateway`. Keep provider keys in environment variables, not in `payment_method.config`.

## Phase 4 notes for the application

- Buying content is one transaction: insert the invoice (final totals, branch = the purchase's branch), insert the `content_purchase` pointing at it, then the
  `content` invoice line pointing at the purchase. When the invoice is paid, set the purchase to `paid`. Access (F3, F4) comes from `canViewContent()`.
- A handed-over purchase must stay `paid` (F6 as written). If a payment for a handed-over book is ever voided, record the return as an invoice adjustment instead of cancelling the purchase.
- Commission accrual runs in the verification transaction (H2, H5, H10, H11): for each lecturer of the course, pick the most specific effective rule, compute base, commission and cap,
  and insert the entry with its snapshots. The database checks the shape and the cap, not the formula. Voiding a payment marks unsettled entries `void` and adds a negative reversal entry for settled ones (H7).
- Payout creation: pick accrued entries (including negative reversals) for the lecturer and period, insert the payout with its final totals, then mark the entries `settled`. If the net is negative, create no payout and carry the entries forward (H8).
  Check in the transaction that payout totals equal the sum of its entries, and in the nightly reconciliation.
- Module gate: `commissions` (H9). A fixed rule larger than the lowest fee of its course should show a warning (H12), which the database does not check.
- Course shares summing to 100 (H3) are still a transaction check when saving a course's lecturers.

## Phase 3 notes for the application

- Publishing is one transaction: build each `exam_question.snapshot` (question, options, correct flags, option keys), set `exam.max_marks`
  to the sum of question marks, then set status to `published`. The trigger refuses it if a snapshot is missing.
- Grade only from the snapshot (G5). Enforce the attempt limit (a count against `max_attempts`), server-time windows and the time limit (G6),
  eligibility (G1), the best or latest rule, and result recomputation (G7) in application code. Check that marks do not exceed `max_marks`.
- A result's `enrollment_id` and `course_id` are optional but come as a pair. Attempts require both.
- Use the module flag `online_exams` and audit result edits after release (J3).

## Phase 2 notes for the application

- Installment amounts must sum to the invoice total (D10, D25), and balances come from the waterfall (E16). Both are transaction work.
- Fee exception billing (D17, D19, D20): resolve the exception active on the period start, bill the alternate option's rate
  or add a negative discount item with `fee_exception_id` and `applies_to_item_id`.
- Notifications: build `event_key` from what caused the event (for example `installment:<id>:due`) so retries cannot send twice.
  Check the channel switch and module flag before inserting. `read_at` tracks in-app reads.
- New permissions in the seed: `fees.override` (D15) and `notifications.manage`. A deployment seeded in phase 1 must insert
  them and its four `notification_channel` rows once (the seed only runs on an empty database).

## Choices made while implementing (review these)

- Status columns are text with CHECK constraints, not Postgres enums, so adding a value is an easy migration.
- A CHECK passes when its condition is NULL. `oneOf` is for NOT NULL columns only, and other checks guard nullable columns explicitly.
  The tests caught two such cases while this was built.
- Added beyond the ER diagram: `notification.event_key` and `read_at` (J2 and in-app reads), `message_thread.created_by`,
  `fee_exception.course_id` (lets a composite foreign key enforce D20), and the extra events `payment_submitted`,
  `payment_rejected` and `installment_overdue` from the notifications section.
- `receipt_counter` is not in the ER diagram. It implements the "per-branch counter" from E13.
- Extra composite foreign keys keep related rows consistent: a fee structure and its course share a branch, a grouped class
  shares branch and subject with its group, a bank payment shares the branch of its bank account.
- `course.status` values (draft, active, closed, archived), ISO weekday numbers (1 = Monday), and the defaults
  (guardian details required under age 16, overdue grace 7 days, action notify, receipt currency LKR) are starting values, not part of the frozen design.
- `src/seed.ts` has a starter permission list and role mapping. Review it before first use.
- `payment_bank_reference_uq` also blocks reusing a bank reference after a payment is voided (the design only frees it after rejection).
- Foreign keys default to no action. Users, students and money records are disabled, ended or voided, never deleted.
- User emails should be lower-cased by the app before saving.

## Tests

`bun run db:test:services` runs 47 scenario and unit tests for the payment services, `bun run db:test:enrolment` runs 42 for enrolment, invoicing and fee exceptions, `bun run db:test:commissions` runs 17 for commission accrual and reversal, and `bun run db:test:promotion` runs 12 for promotion (see Services above).

`bun run db:test` applies all migrations to an in-process PostgreSQL (PGlite), seeds through the Drizzle schema,
and checks 228 rules: the constraints above, the payment verification and void flows, multi-invoice payments,
cancel and reissue, and the append-only audit log. PGlite runs real PostgreSQL code but is not a server:
run the migrations once against a real database (for example the one you will deploy on) before first use.
